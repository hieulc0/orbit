# Orbit Repository Configuration (`.orbit/`)

This directory contains declarative, reproducible Orbit workflow definitions that describe **what** Orbit executes. It is version-controlled and shared across development and CI/CD environments.

---

## 1. Architectural Boundary: Repository vs Host Configuration

Orbit enforces a strict boundary between repository definitions and host/worker execution environments:

```
+-------------------------------------------------------------------------+
|                  Repository-Local Configuration (<repo>/.orbit/)        |
|                                                                         |
|  - Declarative, portable, version-controlled definitions                |
|  - Specifies tasks, workflow dependencies, step graph, and tools        |
|  - Zero secrets, zero machine paths, zero user identities               |
+-------------------------------------------------------------------------+
                                    |
                           Referenced & Submitted
                                    v
+-------------------------------------------------------------------------+
|                    Host/User State Configuration (~/.orbit/)            |
|                                                                         |
|  - Machine-specific runner and worker daemons                           |
|  - Credentials and auth lease storage (OAuth tokens, API keys)          |
|  - Container runtime sockets (Podman/Docker), local scratch directories |
|  - NEVER committed to version control                                  |
+-------------------------------------------------------------------------+
```

### `<repo>/.orbit/` (Committed)
- Contains task graphs, resource requests, step timeouts, and validation rules.
- Defines logical agent requirements (`identity: antigravity-coder`, `binding: antigravity-acp-v1`).
- Completely reproducible across developer machines, staging servers, and CI runners.

### `~/.orbit/` (Host Only - Never Committed)
The target host filesystem layout is:
```
~/.orbit/
├── config.json                  # Orbit server URLs and operator authentication
├── credentials/
│   ├── antigravity/             # Private auth lease storage
│   │   ├── acp_token.json       # Active/leased token (chmod 0600)
│   │   └── settings.json        # Adapter settings (e.g. oauth-personal)
│   └── git/                     # Optional Git credentials
├── daemon/                      # Systemd units, worker launch scripts
└── workspaces/                  # Ephemeral host scratch space for workers
```

## 2. Definitions Directory (`.orbit/definitions/`)

Workflow templates reside in `.orbit/definitions/`:

| Definition | Target Purpose | Verification Command |
| :--- | :--- | :--- |
| `docs-workflow.yaml` | Documentation authoring, refinement, and formatting | Git diff check & docs existence |
| `feature-workflow.yaml` | Feature development, bug fixing, and test creation | Automated build & test (`cargo test`) |

Each definition specifies the standard three-phase lifecycle:
```
code (Agent)
  ↓
test (Independent Container Sandbox)
  ↓
review (Human Operator Approval)
```

### Lifecycle Overview
1. **`code` Step**:
   - The worker claims the assignment and launches the isolated agent container.
   - The agent (e.g. Google Antigravity) receives the task prompt, executes in headless non-interactive mode (`yolo`), and interacts with the workspace via client tool callbacks (`client_view_file`, `client_edit_file`, `client_create_file`).
   - Generates an immutable Git diff patch artifact upon completion.
2. **`test` Step**:
   - Runs in a clean container sandbox without network or agent access.
   - Applies the patch generated by the `code` step.
   - Executes independent test commands (e.g. `git diff --check`, `cargo test`).
3. **`review` Step**:
   - Workflow pauses in state `WAITING`.
   - A human operator reviews the accepted patch artifact and verification logs before approving or denying.

## 3. Credential Handling and Auth Leasing

### Why Secrets Must Remain Under `~/.orbit/`
- Committing secrets, local user paths (e.g. `/home/username/...`), or container socket paths creates immediate security risks and breaks team portability.
- Orbit workers use **auth leasing**:
  - The worker reads credentials from a local private directory (e.g. `~/.orbit/credentials/antigravity/acp_token.json`).
  - The worker verifies private permissions (`0600`), creates a mutual exclusion lock (`.orbit-acp.lock`), and injects credentials ephemerally into the container's scratch directory (`/orbit/home/.gemini/antigravity-acp/`).
  - Upon task completion or failure, the active lease marker is destroyed and the container is cleanly stopped.

## 4. Selecting Antigravity as an Agent Runtime

Definitions request agent capabilities logically rather than by container image name or binary path:

```yaml
agent:
  identity: antigravity-coder
  binding: antigravity-acp-v1
  tools: [read_file, write_file, shell]
  permissions: [workspace.read, workspace.write, shell.execute]
  budget: { calls: 33 }
```

The matching worker on the host registers the `repository.code` capability and maps `binding: antigravity-acp-v1` to its local container launch policy (e.g. `localhost/orbit-antigravity:1.1.1` and `adapter: antigravity`).

## 5. Submitting a Repository Workflow

### Validating a Definition
Before submission, validate the definition syntax and policy constraints:

```bash
orbit validate .orbit/definitions/docs-workflow.yaml
```

Optionally validate with symbolic revision and task overrides:
```bash
orbit validate .orbit/definitions/feature-workflow.yaml --base-revision HEAD --task "Validate sample"
```

### Submitting a Run with Dynamic Overrides
Submit the definition to an active Orbit server, providing task descriptions and symbolic Git revisions at submission time:

```bash
orbit run submit \
  --definition .orbit/definitions/feature-workflow.yaml \
  --base-revision HEAD \
  --task "Implement feature X"
```

Or for documentation tasks:

```bash
orbit run submit \
  --definition .orbit/definitions/docs-workflow.yaml \
  --base-revision HEAD \
  --task "Document worker capability matching and include examples."
```

#### How Symbolic Revision Resolution Works
- The CLI submission boundary resolves symbolic references (`HEAD`, `main`, tags, or short commit prefixes) via Git (`git rev-parse --verify <ref>^{commit}`).
- **Immutable Execution Identity**: The server and workers never receive or defer symbolic names like `HEAD`. Before model validation and server dispatch, `HEAD` is resolved into an immutable 40-character (or 64-character) hexadecimal commit SHA.
- **Subdirectory Discovery**: Running `orbit run submit` from any repository subdirectory automatically discovers the Git repository root to resolve the revision.
- **Non-Mutating**: The underlying repository YAML definition file remains unchanged on disk.

### Legacy Positional Submission
For backward compatibility, submitting an existing definition without overrides continues to work:

```bash
orbit run .orbit/definitions/docs-workflow.yaml
# or
orbit run submit --definition .orbit/definitions/docs-workflow.yaml
```

### Human Review & Approval
When the `review` step reaches `WAITING`, review the patch and record operator approval:

```bash
# Export and inspect generated patch
orbit artifact --output /tmp/patch.diff <RUN_ID> <ARTIFACT_ID>

# Approve review step
orbit approve <RUN_ID> review --comment "Changes verified and approved"
```
